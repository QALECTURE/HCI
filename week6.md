# 5. Topic 1: Personas

## Simple Explanation

A persona is a realistic fictional user profile based on user research.

It represents a group of users who share similar:

* goals
* needs
* behaviours
* frustrations
* context
* digital skill level
* accessibility requirements

The lecture explains personas as fictional characters representing specific user segments, used to understand user needs, experiences, behaviours, and goals. Personas provide the context for task analysis by defining who the users are. 

---

## Bad Persona vs Good Persona

### Bad Persona

```text
Name: John
Age: 25
Likes food
Uses websites
```

This is too basic. It does not help design decisions.

### Good Persona

```text
Name: Aisha Khan
Age: 32
Context: Works full-time and usually orders food using her phone after work.
Goal: Wants to quickly view the menu, check prices, and place an order without calling.
Pain point: Gets frustrated when menu items are not grouped clearly or contact details are hard to find.
Digital skill: Comfortable with mobile apps but does not want a complicated checkout process.
Accessibility need: Needs readable text and clear contrast when using her phone outdoors.
```

This persona helps designers decide:

```text
The website should be mobile-friendly.
The menu should be easy to scan.
Prices should be visible.
The order/contact button should be clear.
Text contrast should be strong.
```

---

# 6. What Makes a Strong Persona?

Effective personas should:

* stay connected to the assessment website
* reflect real user behaviour
* have clear goals
* show pain points
* include context of use
* include accessibility needs
* include scenario-based tasks
* not be based only on assumptions

The Week 6 assessment clinic reminds students that effective personas should stay in context, reflect real behaviour patterns, attitudes and goals, have clear end-goals and scenarios, occupy a clear setting, and show visible pain points.

# 12. Topic 2: Task Analysis

## Simple Explanation

Task analysis means breaking down what users do to complete a goal.

The Week 6 lecture explains task analysis as studying user actions and cognitive processes needed for task completion. It examines current system functions and information flows, helps improve systems, supports precise interface specification, and optimises usability and accessibility. 

Simple version:

```text
Task analysis = understanding the steps users take to complete a task.
```

Example:

Goal:

```text
Order food from a restaurant website
```

Tasks:

```text
1. Open website
2. Find menu
3. Choose food item
4. Check price
5. Find order/contact option
6. Place order or call restaurant
7. Confirm order
```

Subtasks:

```text
Find vegetarian options
Check delivery information
Check opening hours
Find phone number
Check location
```

---

# 13. Why Task Analysis Matters

Task analysis helps identify:

* unnecessary steps
* confusing steps
* missing information
* repeated actions
* high cognitive load
* accessibility barriers
* drop-off points
* poor navigation
* unclear labels
* inefficient user journeys

Teaching message:

> “If the task is difficult, the interface needs improvement.”

---

# 14. Stages of Task Analysis

The lecture describes three main stages of task analysis: gather information, break tasks into subtasks, and analyse tasks. 

## Stage 1: Gather Information

Methods:

```text
User interviews
Observation
Contextual inquiry
Diary studies
Usability testing
Analytics
Think-aloud testing
```

Questions:

```text
What triggers the task?
What is the user’s goal?
What knowledge does the user need?
What tools or information does the user need?
What problems occur?
```

## Stage 2: Break Down the Task

Break the main goal into:

```text
Steps
Subtasks
Decision points
Alternative paths
User actions
System responses
```

## Stage 3: Analyse the Task

Analyse:

```text
Number of steps
Time taken
Task frequency
Physical effort
Cognitive effort
Accessibility barriers
Pain points
Redundant actions
```

# 18. Topic 3: Information Architecture vs User Flow

Students often confuse these.

## Information Architecture

Information Architecture is how content is organised.

Example:

```text
Homepage
Menu
About
Gallery
Contact
Order
```

The lecture explains IA as organising, structuring and labelling content so users can find what they need easily. 

## User Flow

User Flow is the path users take to complete a task.

Example:

```text
Homepage → Menu → Select Item → Order → Confirmation
```

The lecture explains User Flow as the path users take through a website or app to complete a task. 

---

## Simple Difference

```text
Information Architecture = where content lives
User Flow = how users move through it
```

Example:

```text
IA:
Menu page contains starters, mains, drinks and desserts.

User Flow:
User opens homepage → clicks menu → selects mains → clicks order → confirms order.
```

---

# 19. Topic 4: User Flow Diagrams

## Simple Explanation

A user flow diagram shows the journey a user follows to complete a task.

It includes:

* starting point
* user actions
* system screens
* decisions
* success path
* alternative path
* pain points
* final outcome

The Week 6 seminar asks students to create a User Flow Diagram for their assessment, identify task completion and pain points, and receive peer feedback.

# 27. Accessibility in Personas and Task Analysis

The lecture highlights accessibility as something that should be integrated into both task analysis and persona development, ensuring the needs of all users, including users with disabilities, are met. 

## What Students Should Consider

```text
Can the user complete the task with keyboard only?
Can a screen reader user understand the page?
Is the text readable?
Is colour contrast strong?
Are form fields labelled?
Is the process too cognitively demanding?
Are instructions clear?
Are error messages helpful?
Can users recover from mistakes?
```

---

## Accessibility Persona Example

```text
Persona:
David, 58

Context:
Uses a laptop and sometimes struggles with small text.

Goal:
Find the restaurant phone number and opening hours.

Pain Point:
Small text, low contrast and hidden contact details slow him down.

Accessibility Need:
Larger font, high contrast, clear headings, visible contact button.

Design Decision:
Place phone number and opening hours in a clear contact card near the top and ensure strong contrast.
```

# 31. Fun Industry Facts

## Fun Fact 1

Many users do not follow the path designers expect.

That is why user flow diagrams should be tested.

## Fun Fact 2

A persona without a task is weak.

A persona becomes useful when you can say:

```text
This user wants to complete this task in this context.
```

## Fun Fact 3

Reducing one unnecessary step in a checkout process can improve user completion.

This is why e-commerce companies care so much about task analysis.

## Fun Fact 4

Accessibility can change task flow.

For example, a mouse user may complete a task in 3 clicks, while a keyboard or screen reader user may need many more steps if the design is poor.

## Fun Fact 5

AI-generated personas can be useful for brainstorming, but they can also create fake assumptions.

That is why real user evidence is still important.

```text
Do not design the interface first.

First understand:
Who the user is
What they need
What task they want to complete
What steps they follow
Where they struggle
How accessibility affects the journey

Then design the interface.
```

Final message:

> “A good interface is not just visually attractive. It helps the right user complete the right task with fewer steps, fewer mistakes and less frustration.”
