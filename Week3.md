# QHO542 Human Computer Interaction  
## Week 3 Seminar – Interactive AI + HCI Design Sprint

**Seminar duration:** 2 hours  
**Session type:** Practical seminar  
**Main theme:** Designing a learning app interface using HCI principles, AI design tools, usability testing, accessibility, and ethical/legal thinking.  
**Mini project:** Design the first lesson screen for a GCSE Python learning app.  
**Lesson topic:** Variables in Python  

---

# 1. Seminar Purpose

This seminar is designed to be practical, interactive, and industry-relevant.

Students should not only listen to HCI theory. They should apply it like a small UX/product team.

By the end of the seminar, students should understand that:

```text
AI can generate a screen, but HCI makes the screen usable.
```

The key message for students:

```text
Good design is not just about how it looks.
Good design helps real users understand, learn, complete tasks, avoid mistakes, and feel confident.
```

This seminar focuses on:

- visual perception
- cognition and learning support
- accessibility
- Norman’s design principles
- GDPR and BERA compliance
- AI-assisted interface design
- usability testing and reflection

---

# 2. Seminar Scenario

Tell students:

> “Today, you are working as a UX design team. A school wants a web app to help GCSE students learn Python. Your group must design the first lesson screen. The topic is Variables in Python.”

Students are not expected to build a full coded application.

They are expected to design, critique, improve, test, and justify the interface using HCI principles.

---

# 3. Final Student Deliverable

By the end of the 2-hour seminar, each group should produce:

```text
1. An AI-generated or manually sketched first UI design
2. A rough improved wireframe/design
3. Visual perception design choices
4. Cognitive learning support plan
5. Accessibility checklist
6. Norman’s principles mapping
7. GDPR and BERA compliance notes
8. Peer usability testing results
9. One final improvement based on feedback
```

Each group should be ready to present their design in 2 minutes.

# 5. Tutor Opening Script

You can start the seminar like this:

> “Today’s session is going to be very practical. We are not just talking about HCI; we are going to apply it. You will work in groups as a UX team and design a learning app screen for GCSE students learning Python variables. You can use AI tools like Stitch to generate a starting design, but the real work is not the AI output. The real work is your HCI thinking: critique, accessibility, cognition, usability testing, ethics, and improvement.”

Then say:

> “In industry, tools are changing quickly. Designers now use AI to generate UI ideas faster. But AI does not automatically know whether a design is usable, accessible, ethical, or suitable for a specific learner. That is where your HCI knowledge comes in.”

# 9. Simple Explanation of Python Variables

Use this if students are not confident with Python:

```text
A variable is like a labelled box.
You give the box a name.
Then you store a value inside it.
```

Example:

```python
name = "Aisha"
age = 15
score = 90
```

Explanation:

```text
name is the variable name.
"Aisha" is the value.

age is the variable name.
15 is the value.
```

Student-friendly analogy:

```text
[ age ]  --->  [ 15 ]
[ name ] --->  [ "Aisha" ]
```

# 15. Activity 3 – Visual Perception Design

## Time: 15 minutes

Students improve the design using visual perception principles.

Focus on:

```text
Colour
Spacing
Contrast
Typography
Visual hierarchy
```

## Colour

Use colour to guide attention.

Good examples:

```text
Blue for information
Green for correct answer
Red for warning/error
Yellow for hints
```

Bad examples:

```text
Too many colours
Low contrast colours
Using colour randomly
Using red for success
Using colour alone to show meaning
```

## Spacing

Explain:

```text
Spacing gives the user’s brain breathing room.
```

Good design:

```text
Separate the explanation, code, quiz, and feedback sections clearly.
```

Bad design:

```text
Everything is squeezed together with no white space.
```

## Contrast

Explain:

```text
If users struggle to read it, the design has already failed.
```

Good design:

```text
Dark text on light background
Clear contrast on buttons
Readable code block
```

Bad design:

```text
Light grey text on white background
Yellow text on white background
Tiny low-contrast code
```

## Typography

Good design:

```text
Large heading
Readable body text
Monospace font for code
Consistent font sizes
```

Bad design:

```text
Too many fonts
Tiny text
Decorative font for learning content
```

Fun tech fact:

```text
Developers often use monospace fonts for code because every character takes the same width. This makes code easier to scan and align.
```

Deliverable:

```text

Colour:
Spacing:
Contrast:
Typography:
Reason:
```

# 17. Activity 5 – Accessibility Check

## Time: 10 minutes

Accessibility means:

```text
Can different types of users access and use the app?
```

Tell students:

> “Accessibility is not only for a small group of users. Good accessibility improves the experience for everyone.”

Students must include at least 5 accessibility features.

Options:

```text
Readable font size
High contrast text
Keyboard navigation
Alt text for images
Captions for videos
Screen reader-friendly labels
Avoid colour-only feedback
Adjustable font size
Clear error messages
Simple language
Visible focus indicator
Mobile responsive layout
```

## Accessibility Example

Bad feedback:

```text
The answer only turns red.
```

Problem:

```text
A colour-blind user may not understand the meaning.
```

Better feedback:

```text
Red border + warning icon + text explanation:
“Try again. Remember, the variable name goes on the left.”
```

Fun tech fact:

```text
Keyboard navigation is not only for disabled users. Many expert users prefer keyboard shortcuts because they are faster.
```

# 18. Activity 6 – Applying Norman’s Design Principles

## Time: 10 minutes

Students must prove that the design follows Norman’s principles.

| Norman Principle | How It Applies to the Learning App |
|---|---|
| Feedback | Show correct/incorrect response after quiz. |
| Affordance | Buttons should look clickable. |
| Consistency | Same style for Back, Next, Submit buttons. |
| Error Prevention | Give hints before quiz submission. |
| Error Recovery | Allow students to retry an answer. |
| Accessibility | Keyboard navigation and screen reader labels. |
| Mapping | Progress bar clearly shows lesson progress. |
| Load Time | Avoid unnecessary heavy media. |

## Example Answers

```text
Feedback:
The quiz shows “Correct” or “Try again” with explanation.

Affordance:
The Submit button looks clickable and is clearly labelled.

Consistency:
Back, Next and Submit buttons use the same style.

Error prevention:
The quiz gives a hint before submission.

Error recovery:
Students can retry the quiz after a wrong answer.

Mapping:
The progress bar shows Lesson 1 of 5.

Accessibility:
High contrast, alt text, keyboard navigation.

Load time:
Use simple illustrations instead of heavy videos.
```

Fun tech fact:

```text
A progress bar is powerful because users like knowing where they are and how much is left. This reduces uncertainty and motivates completion.
```

```text

Affordance:
```

# 19. Activity 7 – GDPR and BERA Compliance

## Time: 10 minutes

Explain simply:

```text
GDPR is about protecting personal data.
BERA is about ethical educational research and protecting participants.
```

Tell students:

> “If this app is for GCSE learners, especially young learners, we must be careful about privacy, consent, and ethical testing.”

Students answer:

```text
What data does our app collect?
Do we really need that data?
How will users give consent?
How will we protect the data?
How will we avoid harm or pressure during testing?
```

## Examples of Personal Data

```text
Full name
Email address
Date of birth
School name
Phone number
Address
Login details
Quiz scores
Learning progress
```

## Data Minimisation

Explain:

```text
Only collect what you actually need.
```

Bad example:

```text
Collect full name, phone number, address, date of birth and school name just to access a Python lesson.
```

Better example:

```text
Use anonymous nickname or student ID.
Only store quiz progress if needed.
Ask for consent before saving progress.
```

## BERA Considerations

```text
Participation should be voluntary.
Feedback should be anonymous where possible.
Students should not feel judged.
Testing should not cause stress or embarrassment.
No unnecessary personal data should be collected.
```

Deliverable:

```text
Data we collect:
Why we collect it:
Consent method:
How we minimise data:
How we protect data:
BERA ethical consideration:
```

# 20. Activity 8 – Peer Usability Testing

## Time: 20 minutes

Pair groups:

```text

```

The tester completes these tasks:

```text
Task 1: Find the definition of a variable.
Task 2: Identify the code example.
Task 3: Complete the quiz.

```

The observer records:

```text
Did the user complete the task?
Where did they hesitate?
Was anything confusing?
Was feedback clear?
Was the page easy to read?
```

# 23. Fun Tech Facts to Use During Teaching

## Fun Fact 1 – AI Can Design Fast, But Not Always Well

```text
AI can generate a professional-looking screen in seconds, but it may still fail accessibility, learning support, or user context.
```

Teaching point:

```text
Fast design is not the same as good design.
```

## Fun Fact 2 – Users Scan Before They Read

```text
Most users scan a screen first before reading carefully.
```

Teaching point:

```text
Headings, spacing, icons, and visual hierarchy matter.
```

## Fun Fact 3 – Feedback Should Teach

```text
In learning apps, saying “wrong” is not enough.
Helpful feedback explains why the answer is wrong and how to improve.
```

## Fun Fact 4 – Accessibility Helps Everyone

```text
Captions help deaf users, but also help people watching videos in noisy places.
High contrast helps visually impaired users, but also helps users on phones in sunlight.
```

## Fun Fact 5 – Progress Bars Motivate Users

```text
Progress bars reduce uncertainty because users can see how far they have come and what remains.
```

## Fun Fact 6 – Simple Language Is Good HCI

```text
A beginner learning Python does not need complex technical language first. They need a simple mental model.
```

Poor explanation:

```text
A variable is a symbolic reference to a memory location.
```

Better explanation:

```text
A variable is like a labelled box that stores information.
```

## Fun Fact 7 – Dark Patterns Are Bad HCI Ethics

```text
If a design tricks users into giving data or makes it hard to opt out, it may be legally and ethically problematic.
```

```text
Is a minimalist design always better?
```

Expected answer:

